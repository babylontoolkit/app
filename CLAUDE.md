# CLAUDE.md — Babylon Toolkit App Builder (bolt.diy fork)

## Read this first, every session

1. **Read `SPEC.md` before doing anything.** It is the source of truth for scope, architecture, and phasing. If a request conflicts with the spec, say so and propose a spec change — do not silently diverge.
2. This repo is a **fork of bolt.diy** (MIT). `FORK_BASE.md` records the upstream base commit. Respect the inherited Remix code structure; keep diffs against upstream minimal where practical so upstream pulls stay possible.
3. When architecture or scope changes, **update SPEC.md in the same PR** (see SPEC §11 Working Agreement).
4. **Run the gates before declaring ANY task done.** The repo has a husky pre-commit hook that runs typecheck → lint → tests and stops at the first failure. Never hand back work that fails it:
   ```bash
   pnpm typecheck && pnpm lint:fix && pnpm lint && pnpm test
   ```
   Fix everything it reports (`lint:fix` auto-resolves most Prettier/formatting errors). If a gate fails for a reason outside the current task (an upstream defect — see §2.1b), say so explicitly rather than silently bypassing with `--no-verify`.

## What we are building (one paragraph)

**Babylon Toolkit App Builder** (neutral working name, via brand module — SPEC §2.5): a hosted, credit-metered, Bolt-style AI app builder at `app.babylontoolkit.com` that builds **Babylon Toolkit web games only** (BabylonJS + Babylon Toolkit, Vite + TypeScript + React, ESM). Every project starts from an official Toolkit starter template. The agent's knowledge comes from the synced Agent Reference docs and agentskills.io-compliant skills — never from generic web-dev assumptions.

## Standing rules — NEVER violate these in code

- **BUILD-FIRST — BUILD EVERYTHING, ALL PHASES, NOW:** the whole spec (§4.1–§4.15) is in scope for the current build. SPEC §9's phases are LAUNCH/GATING order, NOT construction order — never defer a feature because "that's Phase 3" (wizard, gallery, share/remix, GitHub sync, Game Backends, MCP, billing, admin: build them). Never skip or stub a feature because a key/account/vendor is missing — build it, read credentials from config, degrade gracefully ("not configured" UI state + descriptive server error). Stop building ONLY for (a) a hard technical blocker that physically prevents the code from working, or (b) an explicit instruction from the owner (SPEC §1.3 principle 0, §9, §9a).
- **BINARY FILES ARE FIRST-CLASS (`spec/binary-files.md`):** every file path — template mount, git/folder import, WebContainer writes, snapshots, restore, GitHub sync, share builds, deploys, asset adds — carries binaries as bytes losslessly (base64/ArrayBuffer → `fs.writeFile` with `Uint8Array`). **The WebContainer FS is the single source of truth for binary bytes:** `File.content` is ALWAYS empty when `isBinary` (the map holds `isBinary` + `size` only) — read bytes via `FilesStore.readBinaryFile()`, never `dirent.content`. **NEVER route a binary through a `boltArtifact`/`boltAction`** — it is a text protocol (the action runner UTF-8 encodes it, corrupting it) and it reaches the model; write binaries to the sandbox out-of-band. base64 is a WIRE format (snapshots, deploys, GitHub blobs), never live store state. Upstream's text-oriented file layer MUST be extended, not worked around (SPEC §1.3 principle 10, §4.4).
- **CONTEXT IS A MONEY PATH (`spec/context-budget.md`, SPEC §4.2.8):** **the artifact is a channel to the MODEL that happens to write files; the WebContainer FS is how files reach the project — never confuse the two.** Every byte in a `boltArtifact` is paid for on this turn AND every later turn (it lives in the history forever), and the tool loop re-sends the prefix up to 7× per generation. So: the creation artifact carries **NO file bodies** (the whole starter is written out-of-band; the artifact is just `npm install` + `npm run dev`); **opaque** files — generated (lockfile), vendored/minified (`public/scripts/*.js`), image-ish text (`.svg`) — are declared as `<boltFile>` markers, never shown (`app/lib/context/opaque-files.ts`); and the file-context block is **cached** (a breakpoint caches the prefix up to itself, so it never invalidates the base prompt). The inverse is equally binding: everything the agent must READ (`globals.ts`, `system/platform.tsx`, `classes/`, `vite.config.ts`) stays fully visible. Measured: 1,100,188 → 111,659 input tokens per creation. A regression here throws nothing and breaks nothing — it just silently multiplies the bill. **Any new ingest path must classify its files before they can reach the model; the default for anything generated, vendored, or minified is opaque.**
  - **A user project's `CLAUDE.md` IS its system prompt (2026-07-16).** A root `CLAUDE.md` is lifted out of the file context and pushed as its own **Project Instructions** system block (`agent/project-instructions.ts`, pure + tested) — it was already reaching the model, but as an anonymous file with nothing marking it as instructions. Three rules, each a silent failure: it is **MOVED, not copied** (the proxy deletes the key before `createFilesContext`; sending it twice pays twice on every turn forever and leaves two copies to disagree after an edit); it is **CAPPED** (`MAX_INSTRUCTIONS_CHARS`, since a remix carries someone ELSE'S file and an unbounded one is an unbounded per-turn bill); and it **cannot waive the platform's non-negotiables** — the block states the precedence (platform > CLAUDE.md/SPEC.md > defaults) and tells the model to ignore host-setup directives, because a `CLAUDE.md` written for another host is the COMMON case for an imported project and the real ones say things like "always fetch the Agent Reference at <url> first; if the fetch fails, stop immediately" — which would stall the agent on turn one. Root-only, `CLAUDE.md`-only: `AGENTS.md`/copilot-instructions are protected from overwrite but never promoted.
  - **A dozen more levers hold that number in place — read `spec/context-budget.md` §"The complete lever inventory" BEFORE touching the prompt, the tool set, or the file context.** Three that are easy to undo in good faith: **`babylon.toolkit.d.ts` (~490KB / ~130k tokens) is NEVER baked into the prompt** (editor IntelliSense only — it is bigger than the whole creation context; the agent learns the API from the reference prose + `classes/`); **attachments are capped server-side** (5MB/file, 20MB/msg, 8 max, checked before the credit gate — vision tokens bill normally, so an unbounded upload is an unbounded bill on OUR key); and **the skills index is sorted / prompt builds are hash-skipped** because an unstable prefix busts the cache on *every* generation.
  - **THE HISTORY CARRIES NO FILE BODIES (`llm/history.ts`).** The conversation is UNCACHED (all 4 breakpoints are on the system blocks, so it sits outside the cached prefix) and re-sent at full rate every turn, growing forever — and **83–87% of it was file bodies in `<boltAction type="file">`**, every one a STALE duplicate of what `# Current Project Files` already sends correctly and freshly each turn. Bodies stripped, tags kept (the model must still know which files it touched); user messages never touched; a window bounds it but **never drops the first user message** (the original brief). Measured on real conversations: **−85% (~28k → ~4.3k tokens re-sent per turn)**. ⚠️ **Do not "fix" this by caching the history instead** — a breakpoint before it is invalidated every turn by the volatile blocks that precede it, so you'd pay a 2× cache WRITE in place of a 1× read. That is strictly worse.
- **OUTPUT IS THE OTHER HALF OF THE BILL — AND ALL OF THE WALL CLOCK (`spec/context-budget.md` §"Wasted tokens and dead time"):** input caches; **output decodes SERIALLY at ~60–110 tok/s and costs 5× input**, so a 44k-output-token generation simply CANNOT be fast and no cache will fix it — "make it cheaper" and "make it faster" are the same instruction, and **a latency complaint is never answered with more caching until the step log has been read.** The measured ways we buy tokens that buy us nothing: redrafting around tool rounds (29,173 out = 68% of the bill / 75% of the clock, to load ONE skill); output the user never sees — **measured 2026-07-16 across 10 live creations: thinking is 5–57% of output, scaling with the DIFFICULTY of the ask** (the old "~35k" figure is RETIRED — it described a six-tool-round generation that no longer exists; and **do not infer thinking from `ch/tok`** — that constant is calibrated for prose and our output is code, see §"MEASURED". Price it from the reasoning WINDOW); 90.5s of dead air paying output rate for reasoning returned as EMPTY text; a clean `finishReason:'stop'` with no text and 10,054 billed tokens (now a hard failure → refund); a zod tool-arg violation killing a generation AFTER the tokens were spent (validate in `execute`, never in the schema); hitting the tool cap with no step left to answer (`maxSteps` is `MAX_TOOL_ROUNDS + 1` — the `+1` IS the answer); and re-emitting a whole file to change one line (`type="edit"`). **A Stop is not waste** (billed for what it consumed); a hard failure is OUR waste (user refunded). **⚠️ A FIX CAN BLIND THE METRIC THAT MEASURED IT (2026-07-16):** `wastedOutput` was defined as "sum of all-but-last step outputs" — *waste = extra steps* — which was true until the pathology-1 fix (`allowTools:false` → `maxSteps:1`) made a creation exactly ONE step, whereupon its `steps.length <= 1` guard reported **zero waste on the most expensive generation in the product**, in good faith, forever. Now exact: `steps[].textChars` (we stream the text — just count it) gives **`silentStepOutputTokens`** (output on steps that emitted NO text) + **`charsPerOutputToken`** density — real text runs **~3.5–4 chars/output token**, so a fat step far below that was billed for thinking, not artifact. `outTokens` bundles thinking + tool JSON + text into one provider number and `display:'summarized'` bills the FULL thinking while returning a summary, so a total can NEVER answer "where did the output go". **When you fix a pathology, re-derive whether its metric still measures it** — a metric encoding the SHAPE of the old failure dies reporting zero, which reads as success. The diagnostics that make these visible ARE persisted (`generations.tool_rounds` / `duration_ms` / `finish_reason` / `steps jsonb`, migration 0002) — **keep writing them**: aggregate usage hides every pathology above, and without them the §4.10 dashboards can chart spend but never diagnose it.
- **🔴 ON DISK IS NOT VISIBLE, AND THE MODEL ONLY EVER SEES VISIBLE (fixed 2026-07-16, `registry/mount.ts` `waitForMountVisible`).** Creation wrote the whole starter to the WebContainer (awaited — the bytes were genuinely on disk) and then fired the generation immediately. But the model reads `workbenchStore.files`, which a WATCHER fills **asynchronously**. Measured live: **the request fired at 5405ms with SEVEN files; the store filled at 5531ms with 78.** A 126ms race, and the model was asked to write a racing game having been shown seven files, **none of them source** — no `src/scripts/<Class>.ts` (the class §4.4b had just scaffolded FOR it), no `src/babylon/classes/`, no `globals.ts`, no `vite.config.ts`. **This silently falsified §4.2.8's "everything the agent must READ stays fully visible" on the most expensive generation in the product**, and it announced itself in plain language — the model told the owner *"I did not edit that mode — I can't see its source"* — which was read as caution rather than as a bug report. **When the model says it cannot see something, believe it and go and check.** The fix waits for the store to show the exact files §4.4b produced (sentinels, never a count — a count is a guess that moves when the template does), and it degrades after 15s rather than hanging the New Project button. **⚠️ The wait belongs at the END of `startProject`, never inside `createProjectFromRegistry`** — see the next entry.
  - **The AI SDK sends only COMMITTED render state, so anything set after the last commit is invisible.** `useChat` refreshes its request body from a `useEffect` (`extraMetadataRef`), and `reload()` reads that ref. Putting the wait inside `createProjectFromRegistry` fixed the files and left **`projectId: undefined` on every creation** — the server's ownership check and its per-project attribution both got nothing — because `createProject` sets the atom *after* that function returns, in the same synchronous block as `reload()`. The same bug wearing a different hat, and fixing half of it hid the other half. One wait, after everything that sets state. The comment claiming `projectId` was safe *because* it was "read from the store rather than captured" was wrong: `useStore` **is** a render capture.
  - **A context regression costs $0, throws nothing, and makes the token count go DOWN** — which reads as a *cheaper* turn. Only output quality suffers. That is §4.2.8's stated failure mode, and it is why this survived a full measurement pass that was looking at exactly these numbers.
- **A STREAMING FILTER HAS A TIMING CONTRACT, AND A $0 DEFECT IS STILL A DEFECT (`agent/shell-strip.ts`, `spec/context-budget.md` pathology 11):** the server-side shell strip shipped buffering **every** `<boltAction>` until its close tag — including `type="file"`, whose verdict is decided the instant the opening tag is read. Measured live: a 13,776-char game script reached the browser **51 seconds** after the model started sending it, in one lump (18 text chunks per generation; silences of 51.5s/31.1s/12.6s). Fixed → **157 chunks, max 222 chars, zero silences ≥2s.** The invariant: **the only text that may be withheld is text whose safety is not yet decidable** — a `shell`/`start` command mid-read (~20 bytes; `npm install x` and `npm install x && rm -rf /` share a prefix, so this buffering is MANDATORY) or a partial tag split across a delta (≤12 chars). Both bounded by a TAG's length, never a FILE's. Three ways this hid, each worth generalising: **(a)** the tests concatenated every `push` + `flush` before asserting, so a filter withholding everything until the last byte passed all 8 — `shell-strip.spec.ts` now asserts on the return of a SINGLE `push`, keep it that way; **(b)** the file's own doc comment *claimed* "the artifact still streams to the user in real time", and a false claim in a comment is how it survived review; **(c)** it cost **$0** — every other entry in the waste taxonomy is priced in tokens, which trains the eye to read a $0 defect as "not a problem", and this was simultaneously free and the worst thing about using the product. **A latency complaint is traced to where the time WENT, never explained away** — the step log read `92s · 89 tok/s` (perfectly normal) because the time was lost AFTER the model, and server logs stop at the model; only a client-side chunk trace could see it.
- **PRICING IS TWO NUMBERS IN TWO FILES — AND THEY MUST AGREE (`spec/billing.md`, SPEC §4.6):** `credits = ceil(raw / CREDIT_UNIT_COST_USD * CREDIT_MARGIN)` earns `CREDIT_MARGIN` **only if a credit RETAILS at `CREDIT_UNIT_COST_USD`**. Real margin = `CREDIT_MARGIN × (pack $/credit ÷ CREDIT_UNIT_COST_USD)`. Packs shipped at $0.003/credit against a 3.34× setting → **0.84× on the largest pack**: a ~19% loss per generation, worst on the best customers, and nothing threw. `packMargin()`/`MIN_PACK_MARGIN` assert it now — **never add or reprice a pack/plan without re-running that floor.** **The MODEL does not change the margin, only the volume** (credits are cost-proportional: at `CREDIT_MARGIN = 4.0` [raised from 3.34, 2026-07-18], 9,500 credits ≈ $23.75 of spend on any model; a $90 Pro subscriber nets ~$63 / 73% GM on Opus *and* Sonnet) — so "downgrade to save money" is always a false economy here. **Subscriptions: `invoice.paid` is the ONLY grant path** (it fires for month one too; also granting on `checkout.session.completed` double-credits under a second idempotency key the unique index can't catch), the user id rides on `subscription_data.metadata` (renewals have no session), and **credits never expire or reset — a plan accumulates.**
  - **A MODEL AND ITS PRICE ARE ONE FACT — AND SINCE 2026-07-18 EVERY KIE PRICE LIVES IN THE MARKETPLACE PRICE LIST, NEVER IN ENV VARS (`billing/baked-market-prices.ts` + `market-price-store.ts`, `spec/billing.md` §"The Marketplace price list").** One versioned document prices everything the platform bills — LLM token rates AND the §4.16 per-task media prices (image/video): a baked fallback in code (captured from KIE's public pricing feed at `api.kie.ai/client/v1/model-pricing/page`, which independently confirmed the measured rates to the cent — 4-8 $2/$10, 4-7 $1.425/$7.15, fable-5 $4/$20), overridden by whatever list the admin PROMOTED from **Settings → Admin → Marketplace prices** (immutable versions + pointer in the ObjectStore, validate-before-write with ALL errors reported, rollback only onto bytes that still validate — the §4.4 template-pin rules applied to money; the panel's "Fetch kie.ai feed" is for the operator's EYES and is never machine-applied). **The env price vars are RETIRED and REFUSED if set** (`KIE_INPUT_DOLLARS`/`KIE_OUTPUT_DOLLARS`/`KIE_CACHED_INPUT`/`KIE_CACHED_WRITES`/`PREMIUM_INPUT_DOLLARS`/`PREMIUM_OUTPUT_DOLLARS` → a loud `NotConfiguredError` pointing at the panel — a price var nothing reads is a mis-bill waiting to be believed); `KIE_DEFAULT_MODEL`/`PREMIUM_MODEL` survive as SELECTORS, accepted only if the ACTIVE list prices them. **The still-binding rules, each existing because its absence bills real money and throws nothing:** an unpriced LLM model bills at the most expensive row (`ratesFor` fallback), so "is it configured?" and "do we know what it costs?" stay the SAME question; **cache rates are never quoted in the list** (validation refuses the keys; they derive 0.1× read / **2.0×** 1h-tier write per row, so a half-repriced row cannot be expressed); **media lookup has NO most-expensive fallback** — media debits run BEFORE spend, so unknown model / unmatched options / per-second-without-duration are REFUSED (`lookupMediaPrice` → null); **the sync/async seam is an in-process cache** (`activeMarketPrices()` sync for billing math, `ensureMarketPrices()` at the async doorways — proxy entry, `/api/me`, admin; a failed load serves baked and never blocks a generation); and **the `providerRates` premium injection is non-throwing** so an unpriced `PREMIUM_MODEL` refuses new premium requests without taking settlement down. Precedence is still **`LLM_MODEL` > `KIE_DEFAULT_MODEL` > baked default**, safe only because whatever wins must be priced in its OWN right. The retired-era sub-entries below record how the env-var design failed and stay as history.
    - 🔴 **A MODEL THAT IS PRICED BUT NOT *LISTED* IS BILLED AS ITSELF AND RUN AS SOMETHING ELSE.** `stream-text.ts` (the enhancer path, upstream code) looks the model up in the provider's list and on a miss **falls back to `modelsList[0]` behind a `logger.warn`** — so a priced-but-unlisted `KIE_DEFAULT_MODEL` would run Opus 4.8 while settlement charged the configured model's rates. Wrong model, wrong price, no error. The env model therefore reaches the list via upstream's own `getDynamicModels` seam (`kieEnvModel`). **The proxy hands `model` straight to `getModelInstance` and never had the problem — which is exactly why this would have hidden:** the main money path was correct, so nothing pointed at the other one. Its two readers are deliberate (`kie-wire.ts` is client-importable, so it cannot touch `.server/env`); same variable, two doors, and they must never disagree about its VALUE.
    - ⚠️ `.env.example` set `SIGNUP_GRANT_CREDITS` **twice with different values** (500 up top, 1000 in the billing block). A later line WINS in a real `.env`, so copying the file handed out the Anthropic-sized grant while running on KIE. One value, one writer — the same last-one-wins trap as any other two-writer bug.
- **CREDITS-ONLY BY DEFAULT (`PRO_FEATURES_ENABLED=false`):** the shipping default is Lovable-style — usage credits only. The provider picker, model selector, and API-key fields DO NOT RENDER for anyone; every generation uses upstream's `DEFAULT_MODEL` constant in `app/utils/constants.ts` (`claude-opus-4-8` — the strongest coding model, this being a game-coding product). Setting `PRO_FEATURES_ENABLED=true` is the ONLY way Pro/BYOK UI appears (then gated per-user by the license service, or bypassed for local dev). Model choice is a config property, never a user choice (SPEC §4.1, §4.2a, §4.6.1).
- **ANTHROPIC PROVIDER — do not regress (SPEC §4.2a, `spec/anthropic-models.md`):** keep `@ai-sdk/anthropic ^1.2.12` (never downgrade — 0.0.x cannot parse thinking blocks); keep `stripSamplingParams()` (ai@4 injects `temperature: 0`, which current models 400 on) and `dropOrphanReasoningSignatures()` (empty thinking blocks emit orphan signatures); `capabilities.ts` stays OUTSIDE `~/lib/.server/**` (client bundle imports the registry); `PROVIDER_COMPLETION_LIMITS.Anthropic` stays 64000 (a floor, not a ceiling); model IDs carry no date/`-latest` suffix.
- **THINKING IS ON, VISIBLE, AND ITS COST IS CHOSEN (SPEC §4.2a, `spec/anthropic-models.md` §3.4–§3.6):** omitting `thinking` does NOT disable it — it buys adaptive thinking with `display: "omitted"`, i.e. paying the full OUTPUT rate for reasoning the API hands back as EMPTY text (measured: 90s of dead spinner). `thinkingFetch` sets `display: 'summarized'` (costs nothing extra), and **reasoning streams on its own channel (`g:`), NEVER merged into text** — text feeds straight into the artifact parser, so leaked reasoning gets written into the user's file; thinking alone is also not "produced output" (a think-only generation still fails and refunds, §4.6). **`effort` defaults to `high` SERVER-SIDE**, so sending nothing silently buys the second-most-expensive setting on every generation; we send `medium`. **`low` is DELETED from `EffortLevel` and must never return:** it is 22% cheaper on a creation and *wrong* on an edit — it wrote to `src/routing/router.tsx` (READ-ONLY shell, §4.4c) and abandoned diff-edits for whole-file rewrites. **There is no cheap tier.** The per-turn policy (`effort-policy.ts`) decides by **turn KIND, never by reading the prompt** (a prose classifier puts the model in charge of the bill) and **only ever escalates**: repair → `high`, 2nd repair → `xhigh`, `/slash` → `high`, everything else → the operator default.

- **THE LEDGER IS A MONEY PATH (`spec/billing.md`, SPEC §4.6):** **append-only; balance is DERIVED (latest `balance_after`), never a mutable counter** — and **"latest" means `order by seq desc`, NEVER `created_at`** (migration 0003): `now()` is the *transaction* timestamp, so back-to-back rows tie on it and the tiebreak fell to a random uuid, making the balance read pick a random row from that millisecond. It bit the exact sequence the proxy runs on every failed generation (settle the debit → auto-refund it, in one `finally`), producing a balance that skipped the debit. **Clocks tie and clocks go backwards — never order money by one.** — a counter loses updates under concurrency (two generations read 100, both write 60) and cannot answer "where did my credits go". `balance_after` is computed by the WRITER under a lock (`append_ledger_entry`, a Postgres `security definer` fn with a per-user advisory lock); deriving it in TypeScript reintroduces the exact race. Grant uniqueness and payment idempotency are **partial unique indexes**, not app-level checks — a read-then-write check is a race that a Stripe retry or a second tab sails straight through. **Cache writes bill at 2×, not 1.25×** (we use the 1h tier, §4.2.8); assuming the headline number under-charges every generation and nothing throws. The gate runs ONCE before the model; settlement runs after and **can never refuse** — so a `generation` debit MAY go negative (§4.2.1 forbids killing an in-flight generation for balance), and nothing else may. Failed generations auto-refund; a **Stop** is not a failure and is charged for what it consumed.
- **AUTHORIZATION IS TWO WALLS, AND BOTH ARE LOAD-BEARING (SPEC §4.5.3):** RLS alone cannot protect the service-role paths (grants, webhooks, entitlements) that bypass it BY DESIGN — our project store uses the admin client, so without the middleware there is NO ownership enforcement. The middleware alone cannot survive a route that forgets to call it. `requireOwnedProject` is the only correct way to turn a client-supplied project id into a project, and it reports **404, not 403**, for someone else's project (a 403 confirms the id exists → enumeration oracle).
- **NEVER prefix a platform secret with `VITE_`:** Vite INLINES every `VITE_*` var into the client bundle. Upstream's `VITE_SUPABASE_*` is the USER's game backend (§4.15) and is public by design; ours is the platform DB and its service-role key **bypasses RLS**. Shipping it to a browser hands every visitor every row.
- **Pull compatibility (standing commitment):** stay mergeable with upstream bolt.diy indefinitely — additive-first (new code in new files), hide-don't-delete (flags, never removing upstream code), platform-as-provider (our server proxy plugs into upstream's provider layer). **Hotspots — extend, never rewrite:** the file layer/FilesStore + import paths (binary work: add a module + hook seams, use `isBinary` metadata) and the provider layer (add a Platform provider; never restructure multi-provider — BYOK and `PRO_FEATURES_ENABLED` depend on it). Keep all generation logic server-side so upstream's coming agent/subagent rework can land beneath us. Unavoidable upstream-file edits are minimal and logged in FORK_BASE.md (SPEC §2.1a).
- **Sandbox seam:** no new WebContainer-specific coupling outside bolt.diy's existing runtime layer. Everything sandbox-ish must remain swappable for a server-container provider (SPEC §1.3.5, §8).
- **ALL platform secrets are server-only — and a server route may ACT on a secret, never EMIT one.** Anthropic platform key, AWS keys, Supabase service-role key, Stripe secret, license-service secret: server code paths (`app/lib/.server/**`) only — never in client bundles, never committed, never logged. **Never returned in a response body, either** — upstream's `/api/export-api-keys` was an unauthenticated GET that read every provider key out of `process.env` and returned it as JSON (`curl` → `{"Anthropic":"sk-ant-..."}`). That is worse than an unmetered endpoint: unmetered bills us while it's reachable, a leaked key works **off-platform forever**. It now requires a verified user and reads only the caller's OWN cookie keys — the server env is not consulted, *not even as a fallback* (`upstream-routes.spec.ts` pins it with a platform key present). "Is a key configured?" is a **boolean** (`/api/check-env-key`), never the value. Likewise, any route that can reach a provider key must pass the credit gate or it is not a route, it is a hole (§4.5.4). Local dev values live in `.env.local` (must be gitignored — verify before pasting real AWS keys; leaked AWS keys are scraped from GitHub within minutes); deployed values come from SSM → container env (DEPLOY.md). Platform-credit LLM calls route through the server agent proxy (SPEC §3).
- **Storage is server-side (`@aws-sdk/client-s3`).** Snapshots/builds move through server routes with ownership checks (proxy now; presigned URLs are the planned scaling swap — keep the storage layer behind an interface). Snapshots are a **base64-JSON envelope** of the `Uint8Array`-faithful file map (binaries as base64 entries — this supersedes the original tar design, `spec/hosting.md`); a snapshot→restore round-trip MUST preserve binary bytes exactly.
- **Authorization is two-wall:** every server route touching a project validates session **and** project ownership (middleware), with Supabase RLS as backstop (SPEC §4.5.3). "Logged in" is not authorization.
- **The credit ledger is append-only.** Balance is derived (latest `balance_after`); never a mutable counter. Single bucket; credits never expire (SPEC §4.6).
- **Shell actions are allow-listed** (`npm install <pkg>`, `npm run <script>`), enforced client-side AND stripped server-side (SPEC §4.2, §5).
- **No server-side execution of user code or skill scripts.** Ever (SPEC §5).
- **Generations never depend on GitHub at runtime.** Docs and skills are consumed from synced, versioned snapshots (SPEC §4.3, §4.11).
- **Grant integrity:** signup grant once per user (partial unique index). **BYOK is honored only with a server-verified active Pro entitlement**, and its UI (key entry, provider/model pickers) must not render for non-Pro users at all — credits-mode UI contains zero provider machinery (SPEC §2.3, §4.1, §4.6.1).

## Known upstream defects (SPEC §2.1b — do not re-introduce)

- Binary file layer destroys bytes at ingest → `spec/binary-files.md` (never regress this).
- **Server-side MCP is an unauthenticated RCE (SPEC §4.14, §5).** Upstream's `MCPService.updateConfig` spawns a child process per stdio server, reachable from an unauthenticated `POST /api/mcp-update-config` — `curl` with a `command` runs code on our box. Closed fail-closed: `app/lib/.server/mcp/server-guard.ts` 404s both `/api/mcp-*` routes unless `SERVER_SIDE_MCP_ENABLED=true` (local bisect only). Never auth-gate-and-allow instead — §5 forbids server-side execution outright; MCP runs in the user's WebContainer. Pinned by `upstream-routes.spec.ts`.
- **🔴 THE INHERITED OUTBOUND ROUTES ARE ANONYMOUS SPEND HOLES — AUTH IS PER-HANDLER, NOT IN `withSecurity` (2026-07-19, SPEC §5, `spec/spend-holes.md`).** Bolt.diy ships ~14 routes that reach OUT on the server's behalf, ALL originally unauthenticated. Each cost the OWNER, not the caller, and each fails silently (a token count goes DOWN, nothing throws): **(1) `api.git-proxy.$` was a fully open forward-proxy** — `GET /api/git-proxy/<any-host>/<path>` streamed arbitrary internet content through our box (egress/bandwidth + IP-reputation abuse) and reached cloud metadata / private services (SSRF), and it logged the caller's `authorization` header. **(2) `api.github-user`'s `get_token` returned the PLATFORM `GITHUB_TOKEN`** to an anonymous caller (export-api-keys-class exfil — a leaked token works off-platform forever). **(3) `github-stats`/`github-branches`/`netlify-user`/`vercel-user`/`supabase-user` fall back to a platform provider token** when the caller sends none, so an anonymous request spent OUR quota. **(4) `gitlab-branches`/`gitlab-projects` took a caller-supplied `gitlabUrl` base** (SSRF). **(5) `netlify-deploy`/`vercel-deploy` drove unbounded 60× polling loops** anonymously. **(6) `supabase.query`/`variables`/`supabase` were anonymous passthroughs.** All closed: a `denyUnlessVerified(request, context)` guard (`app/lib/.server/http.ts`) at the TOP of every handler; git-proxy + web-search share `app/lib/.server/net/ssrf.ts` (`assertPublicUrl` — string allow-list + DNS-rebinding guard, re-run on EVERY redirect hop); gitlab base URLs pass `isAllowedUrl`; `get_token` returns the caller's OWN cookie token, never the env fallback. **The auth is IN THE HANDLER, never in `withSecurity`** — that wrapper does method-check + rate-limit + headers ONLY; its old unenforced `requireAuth` option is DELETED (a wall in a boolean nobody reads made every route LOOK protected while anonymous — the same false-confidence class as the pre-fix pattern). Pinned by `outbound-auth.spec.ts` (→ 401 with ZERO outbound `fetch` when unauthenticated) + `net/ssrf.spec.ts`. **Never wrap an outbound route and assume it is authed; grep for `denyUnlessVerified` in the handler.**
  - **🔴 THAT SWEEP WAS INCOMPLETE, AND ITS TEST ENCODED THE GAP AS COVERAGE (2026-07-20, `outbound-enumerate.spec.ts`).** It enumerated routes named after **vendors** and guarded all of them; routes named after **subsystems** were never looked at, and five shipped anonymous for a year behind 21 green assertions. Worst: **`api.system.git-info` preferred the PLATFORM `GITHUB_ACCESS_TOKEN` over the caller's own** — an anonymous `curl` listed the operator's private repos, gists and orgs (strictly worse than the `api.github-user` fallback the same sweep fixed: precedence, not fallback). Also `api.github-template` (caller-chosen `?repo=`, platform token, ≤3 unbounded S3 writes/request), `api.models` (caller-COOKIE `baseUrl` → SSRF via keyless Ollama/LMStudio; cookie-keyed cache evictable to re-hit keyed providers on our quota), `api.system.diagnostics`, `api.bug-report`. All now `denyUnlessVerified`, and git-info reads the caller's token ONLY. **The fix that matters is structural and DEFAULT-DENY**: `outbound-enumerate.spec.ts` walks `app/routes/` and fails any `api.*` handler that references no wall and is not in `PUBLIC_BY_DESIGN` with a written reason. ⚠️ Its first draft scanned for `fetch(` and **missed two of the five** (they reach out via `fetchTemplateFiles`/`LLMManager`, no literal `fetch(`) — **a detector that decides which routes matter reproduces the original bug with a regex instead of a person.** The two specs are complements, mutation-verified: a new unguarded route fails the source scan; a guard whose *result is ignored* passes it and fails the behavioural one. Still flagged-not-fixed: `api.git-info`/`api.system.disk-info` disclose host `git`/`df` output anonymously via `execSync` (fixed commands, no caller input reaches the shell).
  - **The enhancer was NOT a hole — but it lied to the UI (fixed 2026-07-20).** `api.enhancer.ts` has had all three walls since the Stage-3 audit (verified session → `checkCreditGate` → `settleGeneration`). What was broken: it returns a bare text stream, so unlike a generation it emits no `credits` annotation, `applySettlement` never fired, and the displayed balance drifted below the ledger for the rest of the session — money correctly spent, screen saying otherwise, which reads to the owner exactly like a leak. `usePromptEnhancer` now calls `refreshSession()` when the stream ends: re-read the server's balance, never subtract locally. **A settled charge the UI cannot see is a defect even when the ledger is right.**
  - **`kieEnvModel` read only `KIE_DEFAULT_MODEL` while `getPlatformModel` prefers `LLM_MODEL` (fixed 2026-07-20).** Same latent mis-bill the function's own doc comment describes, one variable to the left: a platform model set via `LLM_MODEL` never reached the provider list, so `stream-text.ts` would fall back to `modelsList[0]` and the enhancer would RUN Opus 4.8 while settlement charged the configured model's rates. Both readers now share the precedence `LLM_MODEL` > `KIE_DEFAULT_MODEL`. **Two readers of one variable must never disagree about which var WINS, not just about its value.**
- **Client-supplied byte uploads need a SIZE CAP or they are unbounded S3/egress on our bill (2026-07-19, SPEC §5).** Two verified-user-reachable writes shipped uncapped: the publish build (`share/publish.ts`, `BUILD_MAX_MB` 150 / `BUILD_MAX_FILES` 10k, checked BEFORE decode/write) and the remix seed (`share/seed-store.ts`, `REMIX_SEED_MAX_MB` at `putRemixSeed`, the single choke point for both publish-deposit and self-remix). Two walls bound them to account holders, but "verified" is not "unmetered" — an uncapped write is repeatable per re-publish. `BuildTooLargeError`/`SeedTooLargeError` are in `http.ts`'s `SAFE_ERRORS`. **All caps are env-configurable** (2026-07-22) — a hard-coded ceiling is a code change + deploy for the operator, and every refusal now names the size, the limit AND the variable.
  - **🔴 INDEPENDENTLY-CHOSEN LIMITS DRIFT, AND THE DRIFT IS INVISIBLE (fixed 2026-07-22, `storage/limits.ts`).** The platform stores a user's SOURCE in two places for two reasons — the §4.5.4c working copy (crash recovery, 256MB) and the §4.8 remix seed (75MB, copied from the pre-config constant) — and nothing related the two numbers. A project between them was held for recovery, **published successfully**, and then failed to seed, leaving a public, playable, **permanently un-remixable** game. The owner was told nothing, because `depositRemixSeed` may not fail a publish and "best-effort" had been implemented as a `catch` that logged to a server file; the first symptom is a STRANGER clicking Remix and getting an empty editor. Both defaults now come from `DEFAULT_PROJECT_SOURCE_MAX_MB` (still separately tunable — an operator just has to type it), and `publish-limits.spec.ts` pins the agreement (mutation-verified: restoring 75 fails it). The BUILD cap is deliberately NOT in that family — a `dist/` is served publicly on every play, different economics, its own number. **The lesson generalises past these three: a limit that is only correct RELATIVE to another limit must be derived from it or asserted against it, because nothing else will ever notice.**
  - **A best-effort step that cannot fail the request must still REPORT.** The publish response now carries `remixable` + `remixBlockedReason` and the Share dialog renders it ("This game can't be remixed"). Keeping the publish successful was right; keeping it *quiet* was the defect.
  - **`PUBLISH_BODY_MAX_MB` is DERIVED by default** (`maxPublishBodyBytes` = build + seed + 10%, in `publish.ts` beside the caps it clears, not in the route) — the body carries both, so a third hand-picked number silently becomes the real cap the moment either is raised, refusing with a limit the operator never touched. An explicit override still wins (silently recomputing a typed value is its own mystery), but one below build + seed logs a loud warning **at the moment it refuses**, not at boot.
- `uno.config.ts`: icons render blank when the dev server starts from VS Code's integrated terminal (upstream gates `presetIcons`' loader on `!process.env.VSCODE_CWD`). We register the `ph` + `svg-spinners` collections explicitly — keep it that way.
- `tsconfig.json` excludes `functions/` (Cloudflare Pages entry imports `../build/server`, absent pre-build → `tsc` fails in the pre-commit hook). We deploy to Lightsail, not CF Pages. Keep `functions/` on disk (hide-don't-delete).

## Persistence model — repo-primary (SPEC §4.5.4b) — **BUILT 2026-07-16**

> ⚠️ **AMENDED 2026-07-22 by owner decision (SPEC §4.5.4c) — repo-primary is the OWNERSHIP model, no longer the DURABILITY model. DECIDED, NOT YET BUILT.** Measured: a `/bt-landing` run finished (`finish=stop`, 20,364 out, 8 files), settled **427 credits**, the tab died, and the project re-opened with no redesign, no assets, and no trace in the conversation that it had ever run — the ledger knew, nothing else did. The platform will keep **exactly ONE working copy per project** (`working/{projectId}.json`, key **derived** from the project id like the remix seed, two walls, written on the checkpoint trigger, present whether or not the project is LINKED, deleted with the project by prefix sweep) as a **crash-recovery buffer — NEVER a history** ("keep the last few" is how the deleted `snapshots` table grows back). "Store it only until GitHub sync, then clean up" was considered and **REJECTED: `linked` ≠ `pushed`**, so conditional existence re-opens the hole for anyone who links early and pushes late, and the failure mode of a wrong condition is deleting someone's only copy. **Save is renamed SYNC** — the old label conflated durability with publishing, which is why non-developers lose work. Everything below still holds EXCEPT the flat "stores no project files" claim. ⚠️ **`no-server-storage.spec.ts` needs NO change and must not be weakened** — it pins the absence of the snapshot HISTORY (snapshot routes, `SnapshotStore`, `currentSnapshotId`, client modules referencing a snapshots URL), none of which §4.5.4c reintroduces. Checking that assumption produced the finding: the whole suite stayed green with a working-copy store added, so **that guard would never have caught this returning under a different name** — hence a SECOND guard (`one-working-copy.spec.ts`) pinning the new rule: one object per project, no retention, key derived from the project id, no caller-supplied storage id on the path.

The user's game code is permanently stored in THEIR GitHub/GitLab repo — never on our servers (server = project record + chat only). Browser-only (UNLINKED) until Save = link + push; reload on any device = fetch linked repo + mount. Auto-push on checkpoint defaults ON once linked. LINKED/UNLINKED always visible; nudges are milestone-based and NEVER block generation. `GitProvider` seam (GitHub + GitLab); binary byte-identity applies to provider round-trips; failed saves are LOUD.

**Never regress these — every one of them fails SILENTLY, on the only copy of someone's game:**

- **THE PLATFORM STORES NO PROJECT FILES, AND THE MACHINERY IS DELETED — NOT DORMANT (migration 0007, 2026-07-16).** There is no `snapshots` table, no `SnapshotStore`, no `getSnapshotStore`, and no snapshot route: `POST /api/projects/:id/snapshots` does not refuse, **it does not exist**. Checkpoints are LOCAL (`local-snapshots.ts`, IndexedDB, 20/project). This shipped as "the seam stays dormant as a fallback", which was wrong twice over: an uncalled route that stores a whole project re-opens by being *called*, and 0006 left the table, its index, and a **live RLS policy** standing for a full release after the behaviour was removed — somewhere to write, with the lock on the wrong side of the door. `no-server-storage.spec.ts` now pins it structurally (route files absent, store absent, no client helper, plus a comment-stripped source scan **with a control proving the scanner still works** — a scan that silently matches nothing reports a clean bill of health forever), and `ledger-sql.spec.ts` asserts the schema against the real migrations. Adding a server-side "backup" back is not a backup; it is the old model under a new name.
  - **`current_snapshot_id` → `remix_seed_at`, and the RENAME is the point.** The field kept a real meaning on published projects (it pointed at a remix seed) under a name describing the per-generation history that no longer existed. **A field named for a deleted system is how the deleted system comes back** — a reader finds a full implementation and reasonably concludes we still keep snapshots.
- **The client never holds or sends a git token.** The server resolves it from `git_tokens` (encrypted, **RLS enabled with NO POLICY** — service-role only; a user's own session must not read their own token row). `no-client-token.spec.ts` pins it behaviourally AND at source level. The old flow put a raw PAT in every request body.
- **Save CREATES, never adopts** (`adoptExisting: false`). Save derives the repo name from the project title, so a user with an unrelated `my-game` would have had their repo's HEAD silently overwritten with this game. Collisions walk to `my-game-2`. *Linking* a repo the user named still adopts — that is the correct behaviour for that verb, which is why the flag is required rather than defaulted.
- **Local checkpoints order by monotonic `seq`, NEVER `createdAt`** — migration 0003's ledger bug in a second place. Same-millisecond ties made the tiebreak decide which checkpoint undo restores and which the trim discards.
- **`remoteHead: undefined` (could not ask) ≠ `null` (branch empty).** Collapsing them lets a flaky connection decide the browser is authoritative and push over a repo it never read (`mount-source.ts`).
- **The link is a TUPLE**: `provider` + `linked_repo` + `linked_branch`, all-or-nothing (0006 constraint). It caught two live half-link writers on the way in. A remix is born UNLINKED — `deriveRemix` resets the whole tuple, and the test asserts the PROPERTY, not the fields that happened to exist when it was written.
- **`isSecretPath` is ONE rule in ONE place** (`git/sync-logic.ts`), reused by the remix seed. The narrower rule it replaced (`/\.env\.[^/]*local$/`, mirroring the gitignore convention) **pushed `.env.production`** — the most dangerous file in the family — because it does not end in `local`. Under §4.5.4b every save is a push, so that went from "if you clicked Sync" to "always". Never write a second copy.
- **A RESTORE IS NOT AN OVERLAY, and `protect` is required to make it one (`restore-plan.ts`).** `restoreFiles` shipped writing the incoming map and **deleting nothing** — survivable while it only ran on a fresh container, silent corruption once it runs on a live project: undo left the file it was undoing (§4.12 — the safety net the product sells to non-developers), and "use the version from my repository" produced a THIRD version that is neither (§4.13). Two ways to get the fix catastrophically wrong, both one-liners, both pinned: **(a)** the store holds `/home/project/src/main.ts` and a repo tree returns `src/main.ts` — compare raw and NOTHING matches, so every file is "missing" and the restore **wipes the project** (both sides normalise through the shared `toRepoRelativePath`); **(b)** a repo's map has no `.env` (`isSecretPath` kept it out of every push), so treating it as the whole truth **deletes the user's API keys** — the one file with no other copy. Hence `protect` is a REQUIRED per-call-site answer to "what is this map authoritative about?" (`protectForRepoRestore` = everything but the secrets; `protectNothing` = a local checkpoint, which really is the whole truth), never a default. An empty incoming map deletes NOTHING — a restore is never a wipe.
- **The remix seed is the ONE thing we still store of a user's source** (§4.8) — deposited at PUBLISH, for a game they deliberately made public, `.env`-stripped. It exists because removing server snapshots quietly broke remix: the source pointer became `undefined` for every ordinary project, so a stranger's remix cloned nothing and produced an empty editor with no error. The owner's repo cannot fill the gap (private, and theirs). **`body.files` on `/api/remix` is honoured for a SELF-remix only** — a visitor's files are not the owner's game.
  - **It is one object at a DERIVED key** (`seeds/{projectId}.json`, `share/seed-store.ts`) — never a row, never a stored path. That is a security property, not tidiness: the route it replaced took a caller-supplied snapshot id, which is exactly why it needed `assertSnapshotBelongsTo` to stop project A's owner reading project B's files by naming B's id in A's URL. There is no id to supply now, so `requireOwnedProject` alone is sufficient — **and that stays true only while the key is a pure function of the project id.** Reintroduce a caller-supplied storage id anywhere on this path and the second wall must come back with it.
  - **`GET` only** — the seed route has no `action`, because a write there is server-side project storage under a new name. **`unpublish` DELETES the seed**, and that is load-bearing: "make my game private again" must mean the platform stops holding the source, or §4.5.4b is a claim rather than a behaviour. A clone gets its **own** seed under its own id, so unpublishing or deleting the source never silently empties someone else's remix.

S3 keeps play builds + skill resources + template pins + the remix seeds. **The `ObjectStore` itself is load-bearing and stays** — it is the *snapshot layer on top of it* that is gone.

    **The measurement that found it (2026-07-16, the first edit turns ever run).** One real session, four turns after a 513-credit creation that wrote a complete playable game (30,475 out, 384s):

    |---|---|---|---|

    | edit 2 | 87,257 / **223,654** | **831** | **1.6× — MORE than the whole game** |

  - **A PROJECT HOLDS MANY CHATS (§4.5.6, BUILT 2026-07-16) — and the obvious key is data loss.** "New chat, same game" gives a fresh context on a game already being built (files stay, history does not come along) — the escape hatch for a spec→plan→execute loop that otherwise re-sends the spec discussion on every execute turn, since the history is UNCACHED and re-sent at full rate forever.
