### What already exists (and is already tested)

- **The seam** — `app/lib/.server/git/provider.ts:182` declares exactly five methods: `getCurrentUser`, `ensureRepo`, `getDefaultBranch` (`:210`), `getBranchHead` (`:213`), `fetchTree` (`:221`), `fastForwardPush` (`:224`). `getDefaultBranch` is the precedent this feature copies twice over: it takes the **coordinate** (`Pick<RepoRef,'owner'|'repo'>`) because a branch is meaningless when you are asking *which* branch, and **absent is `null`, failure throws** — the distinction `selectMountSource` depends on.
- **Branch creation is already reachable through the seam and has no caller.** `FastForwardPushInput.createBranchIfMissing` (`provider.ts:154-168`) is implemented on GitHub (`github.ts:464` `git.createRef`) and GitLab (`gitlab.ts:433-447` — committing to a non-existent `branch` with no `start_branch` creates it). No call site passes it today. There is **no `POST /repository/branches` call anywhere in the codebase**.
- **The ingest guard is already factored and already covers two doors.** `assertFetchedTreeUsable(files, { context, operation })` (`clone.ts:360`), `TreeIngestOperation = 'import' | 'sync'` (`clone.ts:92`), `CloneTooLargeError` (`:95`) and `LfsPointerError` (`:118`) both take the operation purely so the refusal *wording* varies by door. The route's `pull()` helper (`api.projects.$projectId.github.ts:531`) runs it at `:551`, **before** the pointer move at `:553`.
- **Both walls are already on every op** — `requireVerifiedUser` (`:198`) + `requireOwnedProject` (`:199`) run before the `op` switch, and `requireOwnedProject` throws `NotFoundError` (404, `ownership.ts:23`) for someone else's project.
- **Per-user rate limiting exists** — `enforceUserRateLimit({ userId, bucket, rule })` (`security/user-rate-limit.ts:154`), `CLONE_RATE_LIMIT` (`:123`), called before any outbound work at route `:227`.
- **The restore half is complete** — `FilesStore.restoreFiles(files, { protect, onProgress })` (`files.ts:1087`) wraps itself in `withRestoreInFlight` (`:1105`), filters `MAP_EXCLUDED_DIRS` (`:1132`), and deletes via `planRestore` with a **required** `protect` (`restore-plan.ts:64`). `protectForRepoRestore` is `isSecretPath` re-exported (`restore-plan.ts:100`).
- **The progress surface is complete and needs no new component.** `WorkspaceSplash` (`BootScreen.tsx:169`) already renders over a live workspace at `z-50`, `coversWorkspace` is *"every phase except `idle` and `failed`"* asserted over the **declared union** read out of source (`boot-progress.spec.ts:108-116`), the progress bar is drawn only for `step === 'files'` (`BootScreen.tsx:90`), and the elapsed clock already rides at the end of the detail line after 5s (`BootScreen.tsx:112-117`). Requirements 91 and 93 are therefore satisfied by *declaring phases*, not by writing UI.
- **The chip is the right parent and already behaves.** `GitStatusChip.client.tsx` (note: `.client.tsx`, and it takes **no props**) sets `modal={false}` at `:116` with the reason documented at `:109-115`, and every string it renders comes from `describeSaveStatus` (`save-status.ts:113`).

### Nine findings that change the plan versus the spec

1. 🔴 **Requirement 22 is ALREADY the shipped behaviour — the task is an entry point, not an install policy.** `ensureProjectRunnable` (`ensure-runnable.ts:112`) runs `npm install` **unconditionally** at `:159`, and its header (`:38-41`) already records the rejection of the conditional design for the same reason the spec re-derives: *"The old code asked `decideDependencyInstall` about a FILE MAP, which is a stale, watcher-filled copy."* So requirement 23 needs no argument won and Acceptance 17's source assertion is nearly true today — what the switch actually needs is a way to **invoke and await** that mechanism outside a mount.

2. 🔴 **`ensureRunnableOnce` returns `Promise.resolve()`, not the run — so awaiting it is a no-op, and the splash's `finally` would fire before the install starts.** `useChatHistory.ts:910` deliberately returns a resolved promise (the shell is spawned by a `<Terminal>` that does not render until the mount resolves, `:784-789`), which is exactly why `mountProjectFiles`'s `await ensureRunnableOnce(pid)` at `:428` does not hold the mount open and why the 🔴 NEVER-`bootProgress` comment at `:854-865` exists. A branch switch that calls it and wraps the call in `try/finally { endBootPhase() }` **passes every unit test and takes the splash down at the moment the 30 seconds begins** — silently destroying the entire justification for requirement 22 (requirement 27: *"the splash is not a nicety attached to that decision; it is the half that makes the decision defensible"*). The switch needs an **awaitable** entry point that returns the real run promise. Note the single-flight (`runnableInFlight`, `:796`) is per PAGE LOAD but is cleared in a `finally` (`:893`) — *a finished run is not remembered* — so re-running within one load is already legal; the blocker is `mountedThisLoad` (`:368`) inside `mountProjectFiles`, which the switch must not go through at all (see finding 4).

3. 🔴 **`refreshSavedCopiesSoon` is the WRONG call for requirement 29, and using it breaks requirements 21 and 45.** It is the *top-up* mechanism: it creates a `kind: 'top-up'` checkpoint labelled `'Unsaved changes'` (`refresh-saved-copies.ts:75`) and ends with **`unsavedWork.set(true)`** (`:230`). A switch and a discard both end in a state that is byte-identical to the branch head, where requirement 21 demands `markSynced` + `unsavedWork.set(false)`. Calling it would write a spurious second checkpoint and then report unsaved work on a clean tree. §4.5.4c invariant 4 says *"every trigger writes BOTH"* — it does **not** say "call the top-up helper"; the correct discharge is `createLocalSnapshot` → `markSynced` → **`writeWorkingCopyFromStore(pid, snapshot.seq, undefined)`** (`working-copy-writer.ts:130`) directly, which is what `checkpointProject` itself does (`useChatHistory.ts:2060-2093`).

4. 🔴 **`mountedThisLoad` and `decideLiveSandboxIsTruth` both make the mount path unusable for a switch — by construction, and that is the safe answer.** `mountProjectFiles` short-circuits on `mountedThisLoad.has(pid)` (`useChatHistory.ts:371-382`), and `decideLiveSandboxIsTruth` (`mount-source.ts:207`) returns **true** for `local | diverged | working`, which would make the mount call `refreshFiles()` instead of restoring — silently turning the switch into a no-op (spec edge case 26). The switch therefore drives `workbenchStore.restoreFiles` **directly** and never re-mounts. This wants a source-level assertion, because "reuse the mount" is the obvious-looking refactor.

5. 🔴 **`#deletedPaths` is worse than the spec's edge case 25 says: it is GLOBAL and PERSISTED, not per-tree.** `files.ts:157` backs a `localStorage['bolt-deleted-paths']` key (`#persistDeletedPaths` `:1471`, loaded in the ctor `:174-183`), it is not keyed by project *or* branch, `refreshFiles` honours it as a `skip:` predicate (`:866`), and **there is no reset API**. So a file deleted on branch A stays invisible on branch B — and, pre-existing and out of this feature's scope, invisible in a *different project*. This feature adds the reset API and calls it from the tree-replacing doors; the global keying is flagged for §10 rather than migrated here.

6. 🔴 **`resetAllFileModifications` is called from exactly three places and no restore path is one of them** — `workbench.ts:811` (file action), `:834` (edit action), `Chat.client.tsx:2916` (after the modified-files artifact is posted). Requirement 28 is correct and the failure is exactly §4.2.8's: nothing throws, the model just computes every later `type="edit"` against a tree that no longer exists.

7. ⚠️ **`planRestore` REFUSES an empty incoming map by design** (`restore-plan.ts:72-74`: *"A restore is never a wipe"*). Spec edge case 1 is therefore already enforced one layer down, but silently — a switch to a commit-less branch would restore nothing and report success. The refusal must happen **before** the restore, in the decision core, with a sentence.

8. ⚠️ **`enforceUserRateLimit` never passes `subject`**, although `RateLimitedError`'s ctor takes one and defaults it to `'repository imports'` (`user-rate-limit.ts:140`). A `create-branch` bucket added today tells the user they made *"too many repository imports"* — a refusal naming the wrong operation, which `spec/fail-loud.md` treats as the same class of defect as a refusal naming no cause.

9. ⚠️ **`SaveQueue` has no cancel or drain** (`save-queue.ts:65`): `request()` returns `undefined` when coalesced (`:83-92`) and the running push re-reads files at push time (`useChatHistory.ts:967-975`). So a queued save landing after a switch pushes the **new** branch's files under the old turn's summary. Spec edge case 9 is real; the cheapest correct answer is to refuse the switch while `saveState.status` is `saving`/`retrying` and let the user wait, rather than inventing a cancel path into the one sanctioned push writer.
