### What already exists (the feature is a verifier bolted to existing parts)

### Traps that will bite an implementer

- **A new column must be nullable or defaulted.** `ledger-sql.spec.ts:94-99` inserts `(id, user_id, model)` only; a `not null` column with no default breaks that helper and every FK test behind it.
- **The enhancer only ever gets the ANCHOR write** (`api.enhancer.ts:247` → `settleGeneration`, no enrichment step). Any field written only by the proxy's enrichment is absent on enhancer rows by design — say so in `FIELD_COVERAGE`, do not "fix" it.
- **`fingerprintFromHashes` (`store.ts:132`) is module-private.** Either export it (one word) or compose `sha256` in the new module. Do not write a second hash helper.
- **`shell-strip` / `protocol-strip` report via `captureMessage`, not `alert`** — the shared convention is the `scope` string, not the method.
- **`sharedRateWindow` fixes its config on FIRST use.** A second caller with a different threshold silently gets the original window.
- **A guard that throws under VITEST cannot be tested from the outside.** The throwing path needs an explicit seam (an injected mode), or the very test that proves reporting works will die on the throw.
- **Media rows are `gen_`-prefixed siblings.** `refundKind()` (`admin/refund-report.ts:102`) already splits `med_` from `gen_`; `buildUsageReport` does not, and today counts media renders as generations — skewing `failureRate`, `avgToolRounds` and `byModel` on the live Admin tab.
- **There is no `proxy.spec.ts`.** Every "extend proxy.spec.ts" instruction in the feature spec means *create it*.
- **`historyStats` measures only the post-compaction MESSAGES** (`proxy.ts:1848`) and counts no `system[]` bytes. Edge case 12's cross-check applies to the message half alone.

### Decided here, so execute does not have to

- **Two migrations, not one.** `0023` carries the three repair columns (Phase 1 stands alone); `0024` carries the two feature columns. If the run stops after Phase 1, no unused column ships.
- **INV-3(b) is recording-only**, per the feature spec's decided Open Question 1. No suppression hook ships here — the consumer and the promotion both land in `_specs/github-branch-client_plan.md` T15.
- **The fingerprint lives in its own module** (`request-fingerprint.ts`), and the *call* is pinned inside `startStream` by a wiring scan. The `countCacheBreakpoints` precedent argues for `proxy.ts`; the size of this one argues against.

### Sequencing — Phase 1 is a genuine stopping point

**Phase 1 (T1–T5) repairs a live production defect and is independently valuable.** Today, on Postgres, a §4.2a refusal fallback — a *different model serving the turn* while billing at the requested model's rates — leaves no trace at all. Phase 1 closes that and makes another silent drop impossible. Stop after T5 and nothing is half-built.

**Phase 2 (T6–T11) is the fingerprint** and depends on Phase 1's `FIELD_COVERAGE` mechanism. **Phase 3 (T12–T15) is the naming, the stale-test repair and the spec write-back.**
