# Spec for model-visible-invariant

branch: project/feature/model-visible-invariant
design_system: DESIGN.md
spec_impact: yes

## Summary

DeepSeek's `dsh` harness (read 2026-08-21) enforces one rule we enforce by hand: **"model-visible means logged"** — anything reaching a model request must be reconstructable from the record, asserted at runtime rather than argued in review. Ours is the same rule spread across a dozen per-path tests, each written *after* an incident taught it to us. This feature takes that idea and **only** that idea: a **request fingerprint**, computed at the one seam every model request passes through, recorded beside the generation, and checked against a small set of invariants that fail LOUDLY into monitoring rather than into the user's turn. It carries two smaller riders — **naming the three phases the existing filters already sit in** (a documentation + source-scan job, explicitly *not* a rewrite), and **recording the foundation decision** that bolt.diy stays the base and `dsh` was evaluated and rejected as one.

⚠️ **The brief's justification needed auditing before it could become requirements, and the audit changed it.** The brief says a single runtime assertion "would have caught the 7-files-not-78 mount race, the double-keyed file map, and the history carrying stale bodies". Retrospectively true. But research found that **all three of those incidents have had their original trigger structurally removed by unrelated changes** — creation no longer fires a generation at all (§4.4a; `Chat.client.tsx:2010-2033` says so in as many words), the file context is now a ~704-token manifest rather than file bodies, and compaction is live and tested. So the honest case for this feature is **not** "it would have caught those three". It is that in all three the same thing was true and **is still true today**: *nothing anywhere reconciles the facts we recorded with the request we actually sent*, so the CLASS recurs through whatever door is next, silently, exactly as it did three times before. Research found two live instances already (see *Two live defects*), which is the argument the brief was reaching for.

## Project Spec Alignment (from SPEC.md — REQUIRED)

### SPEC.md sections this feature relies on or must conform to

- **§4.2 Agent & Generation Loop.** Item 2 (*"Server assembles the request"*) is the subject of this feature. 🔴 The binding constraint is the section's own **agent architecture stance**: *"single agent + server-side tool loop + self-healing repair turns… **do not re-architect**"*. That is why the second half of this brief is **naming**, not building: no plugin registry, no event bus, no Cordis, no config-composed pipeline. The call order stays a call order; what changes is that the phases have names and a test that keeps the names true.
- **§4.2.8 Context Budget — what the model is allowed to see (money path).** This feature is that section's missing verifier. Its stated failure mode is the one being closed: *"A regression here throws no error and fails no build; it silently multiplies the input bill."* The fingerprint must itself obey the section — it is never sent to the model, never enters `system[]`, and is computed **after** assembly so it cannot perturb a byte or invalidate a cache entry.
- **§4.2a / `spec/anthropic-models.md`.** The refusal fallback swaps the serving model mid-stream via `fallbacks:[…]` and records `fallbackHandoffs` *"which is what keeps that visible"*. See *Two live defects* — on Postgres it does not.
- **§4.5.4b/§4.5.4c + `no-server-storage.spec.ts` + migration 0007.** 🔴 **The platform does not store project files, and this feature must not become a way to.** A recorded request would contain the assembled system blocks and a compacted history that may carry ~20 MB of attachments. - **§4.10 Admin + §5A Observability.** The monitor **never throws** (*"observability can't become an outage"*) and is fire-and-forget. A new `AlertSignal` joins the closed union in `monitoring/events.ts`; `scope` strings are free-form and already carry `'shell-strip'` / `'protocol-strip'` precedent.
- **`spec/fail-loud.md`.** Three rules bind directly: **rule 3** — *"a best-effort step that cannot fail the request must still REPORT"* (the de-dup backstops fix silently today, which is the whole reason a double-keyed map cost 22.5k tokens/turn unnoticed); **rule 6** — *"a guard is only real if a test fails when it is removed"*; and **rule 9** — *"when you fix a pathology, re-derive whether its metric still measures it"*, which is exactly what the audit above did to the brief's own premise.
- **`spec/context-budget.md`** — §"The complete lever inventory", §"Where it lives", and §"How to re-measure" (the ~150k first-build-turn threshold). This feature adds a row to the inventory and a verifier for several existing rows.
- **§4.5.3 / §5.** No new route, no new client surface, no user-supplied input reaches the fingerprint path. The Admin read is behind the existing admin wall.

### Two live defects this feature must resolve rather than inherit

1. 🔴 **On Postgres, four recorded fields are silently dropped — including the one that records that a DIFFERENT MODEL SERVED THE TURN.** `GenerationRecord` declares `rawStops` (`generations.ts:116`), `fallbackHandoffs`, `blocksLoaded` and `totalTokens`; no migration creates columns for them, `SupabaseGenerationStore.upsert` (`:344-379`) simply does not mention them, and `toGenerationRecord` returns `blocksLoaded: []` (`:474`). In production it does not. This is the feature's own subject matter, already live, already invisible, and it shipped as a fields-added-to-the-type-but-not-to-the-migration gap — the same silent shape the guard exists to catch.
2. ⚠️ **The file-map de-dup rule now exists in two implementations, on two paths, with nothing cross-checking them.** `createFilesContext`'s backstop (`llm/utils.ts:91-103`) — the one CLAUDE.md credits, with the measured 14-files/22.5k-token evidence — is **not on the agent path at all**; its live consumers are the inherited `/api/chat`, `/api/llmcall` and `/api/enhancer` routes. The agent path's backstop is `buildFileManifest` (`file-manifest.ts:69`, `:79-83`), same rule, separate code, separate test. That is a straight violation of this codebase's own `isSecretPath` rule (*one rule, one place*), and it is exactly the half-of-a-pair-guarded shape the repo keeps rediscovering.

## Functional Requirements

### A. The fingerprint — what is computed, and where

1. **One seam: `startStream`.** The fingerprint is computed inside that closure, over the exact `messages` array and `tools` object being handed to `_streamText`. It is the only placement that sees all SIX call sites, and 🔴 **the only one that sees the re-issues** — the tool-free retry, the forced continuation, the unproductive rescue and the creation-completeness pass each splice in synthetic system and user messages (the same-as-first retry does not: it re-sends byte-identical arrays, differing only in the `thinkingMode` the final retry carries — ⚠️ **as written this said the last TWO retries ran thinking-disabled, which was true of the code and not of the intent; the units defect behind it was fixed 2026-08-21, after this spec was written**) that **no persisted record has ever said the CONTENT of**. ⚠️ Narrowly: `finish_reason` has named WHICH re-issue ran since migration 0002; what nothing carried is the request itself.
2. **One fingerprint per stream start, kept as an ordered array.** A turn that re-issues produces two or more; the record carries `requests: RequestFingerprint[]` with each entry naming its `kind`. ⚠️ **CORRECTED during planning (2026-08-21): there are SIX kinds, not five** — `first | provider-retry | provider-retry-tool-free | forced-continuation | unproductive-rescue | creation-completeness`. The provider retry has two materially different shapes and the plan's research found them at two adjacent call sites: one re-sends the original request, the other **drops the tool DEFINITIONS outright** and splices a synthetic `# Media already generated for this request` block between the system array and the conversation. Those differ in the tool set AND in the system array, i.e. in precisely what a fingerprint exists to expose, so they get distinct kinds. **And `kind` is a REQUIRED positional parameter of `startStream`, never optional-with-a-default** — a seventh call site must be a compile error rather than an unlabelled fingerprint (verified: `TS2554`). Collapsing them to one loses the fact the feature exists to expose.
3. 🔴 **Hashes, counts and short strings — NEVER bodies.** Per system block: `{ role, chars, sha256, hasBreakpoint }`. For the messages: `{ count, chars, sha256 }`. Plus `toolNames` (**offered**, sorted), `toolChoice`, `maxSteps`, `maxTokens`, `effort`, `thinkingMode`, `model`, `provider`, `breakpointCount`, `manifest { entries, sha256 }`. Recording the request itself would put assembled system blocks and a possibly-20MB attachment payload on our disks, which is what §4.5.4b, migration 0007 and `no-server-storage.spec.ts` exist to prevent.
4. **The hash function is the existing `sha256` from `prompt/store.ts`** — not a second implementation, and not a cheap non-cryptographic hash whose collisions would make a mismatch report unfalsifiable.
5. 🔴 **The fingerprint must be DETERMINISTIC for identical input.** Any object serialized into a hash has its keys sorted first, and `toolNames` is sorted. An unstable hash makes every comparison a false positive, mutes the alert within a day, and is the same class as *"the skills index is sorted / prompt builds are hash-skipped because an unstable prefix busts the cache on every generation"*.
6. **It costs nothing the model can see.** Computed strictly after assembly; it reads the arrays and mutates nothing. It never appears in `system[]`, never in a tool schema, never in an annotation the model can read back.
7. **Attachments are fingerprinted by reference, never by content.** Hashing a 20MB image on every turn is a real cost for no information; the count and the `attachmentTokens` estimate `historySize` already computes are the record.
8. **`countCacheBreakpoints` is recorded rather than discarded.** It is computed every turn and thrown away. ⚠️ Research found the clamp is currently **dead code in practice** — at most three breakpoints are emitted since the file-body zones were retired, so one of the four is spare. Recording the count is how a regression back over the limit becomes visible before it becomes an HTTP 400.

### B. The invariants asserted at that seam

9. **Each invariant is a pure, exported, separately-testable predicate over the assembled arrays** — the `countCacheBreakpoints` shape, not logic buried in the closure.
10. **INV-1 — no duplicate project-relative path.** No two entries in the manifest normalise to the same `toProjectRelativePath`. The de-dup backstop already collapses them; this makes the collapse **report** rather than merely happen (`spec/fail-loud.md` rule 3), naming the paths and the two spellings. And the same predicate is applied to **both** implementations, closing live defect 2.
11. **INV-2 — no file body survives compaction.** After `convertToCoreMessages`, no assembled message contains a `<boltAction type="file"|"edit">` whose body exceeds the `OMITTED` marker's length. ⚠️ This is asserted **post-conversion**, which is the gap `history.spec.ts` structurally cannot reach: it tests the regex against `Message[]` fixtures it builds itself, so a client shipping a **third** carrier is invisible — and its own header records that this trap has already fired once, when `parts` was added beside `content`.
12. **INV-3 — the manifest did not silently shrink.** Two checks, because the server cannot know the true file count: **(a)** on a **first build turn**, the framework sentinel must be present in the manifest — ⚠️ **the sentinel ONLY, as shipped: see Known gaps #1.** The §4.4b scaffolded class's NAME is a client-side fact the server is never told, and the heuristic stand-in was built, tested and rejected because it fires on every legitimately imported project — the same paths `waitForMountVisible` waits for client-side, verified for the first time by the party that actually builds the request; **(b)** for any turn, an in-process last-seen fingerprint per chat flags a manifest that shrank by more than a configured fraction. ⚠️ (b) is explicitly **best-effort and non-durable** — the `GenerationStore` has no `get(id)` and no query-by-chat, and adding one for an alert is not worth a store change. 🔴 **And (b) ships RECORDING-ONLY, not as an alert** (Open Question 1, decided): the `github-branch-client` feature is planned next, and **a branch switch is a legitimate large file-map change on every single use** — switching from a feature branch with 90 files to a default branch with 60 is exactly the shape this check watches for, and it is correct. Promoting (b) to an alert before that feature can suppress it would make the channel noisy in week one for precisely the users adopting the new feature, and a muted channel is the same as no guard. Recording-only also means this spec ships **no dormant suppression hook** — the consumer and the promotion land together, in the branch feature.
13. **INV-4 — the recorded model is the model that served.** Closes live defect 1: a fallback handoff must reach the record on every store backend.
14. 🔴 **A violation NEVER fails the generation in production.** It reports: a monitor `alert` under a new `REQUEST_INTEGRITY` signal, and a persisted field on the record. `spec/fail-loud.md` sanctions exactly two silent swallows and *"observability itself"* is one of them — a guard that can take down a paid turn is worse than the defect it watches for.
15. **It DOES throw under test.** In `VITEST`/non-production the violation throws, so a regression fails a suite rather than a dashboard nobody reads. This is the property that makes the guard worth having; without it the feature is a chart.
16. **The alert is rate-limited**, on the `failure-rate.ts` rolling-window pattern. A per-turn alert on a systemic mismatch is a pager that gets muted, and a muted pager is the same as no guard.

### C. Persisting what production silently drops

17. **A migration adds the missing columns** — `raw_stops`, `fallback_handoffs`, `blocks_loaded` — and `SupabaseGenerationStore.upsert` writes them. `totalTokens` stays derived on read; it is correctly derivable and a stored copy is a second writer that can disagree. ⚠️ **CORRECTED (2026-08-21): the derivation has a stated PRECONDITION, and the plan's research briefly concluded the opposite before re-deriving it.** `accumulateStepUsage` computes `Σ max(0, wireTotal − (stepPrompt − uncachedPrompt))`, which equals `promptTokens + completionTokens` **only because `ai@4`'s `calculateLanguageModelUsage` guarantees `totalTokens === promptTokens + completionTokens` per step** — a fact about the SDK, not about arithmetic. Both floors were probed and neither can clip on that shape. So it is `derived`, the formula and its precondition are written into the `FIELD_COVERAGE` reason, and a non-SDK usage source would break it silently. ⚠️ **There is a FIFTH dropped field the brief did not name: `chatId`**, written to `message_id` since the store existed and never once read back — so live defect 1 is five fields in three different shapes (no column; a fabricated `[]` on read; write-only), which is why the guard is structural rather than a list.
18. **New columns for this feature**: `request_fingerprints jsonb` and `integrity_issues text[]`. Bounded by construction (one small object per stream start, `maxSteps`-bounded), following migration 0002's stated reasoning for `steps jsonb`: *written once, read whole, never joined or filtered on*.
19. 🔴 **A field on `GenerationRecord` with no column is a defect, not a degradation, and it must become impossible to add another one silently.** A test asserts that every field the type declares carries an explicit answer: written by the store, filled by a DATABASE default (⚠️ a third kind the shipped `FieldCoverage` needed and this line originally omitted — `createdAt` is neither store-written nor derived), or derived-on-read with a reason. That test is the actual fix for live defect 1; the migration only fixes today's four instances.
20. **`effort` and `toolsOffered` are recorded** — both are decided per turn (`effortForTurn`; the tool object built alongside it) and neither is recoverable today. `steps[].tools` records tools **called**, which is a different fact.

### D. Naming the seams — documentation and a scan, not a rewrite

21. **Three phases, named, with every existing participant classified**: **ASSEMBLE** (runs while `system`/`coreMessages`/`tools`/`model` are being built — everything above the `startStream` closure in `proxy.ts`, and the closure's own body, which is the last thing to touch the arrays), **STREAM** (wraps the model's output), **TOOL** (enforced inside a tool's `execute`, or handed to the SDK as a per-call hook or step cap).
22. **The classification is recorded in `spec/agent-seams.md`** with the entry point and invocation site for each participant, so the document can be checked against the code rather than believed.
23. **Participants that straddle a boundary are named as straddlers**, because pretending they fit cleanly is how the document starts lying. `stripReplayedReasoning` runs on stream output **in order to assemble a second request inside the same turn** — which is precisely why the invariant must evaluate at all assembly points and not only the first. ⚠️ **CORRECTED (2026-08-21) in two ways.** First, this said "two" and there are more: `tool-policy.ts` and `budgets.ts` are ASSEMBLE+TOOL (decided during assembly, enforced as a step cap and inside every `execute` — which is exactly why `budgets-wiring.spec.ts` exists), and `gate.ts`, `cache-warmer.ts`, `preload-skills.ts`, `creation-plan.ts`, `capabilities.ts`, `retry-policy.ts`, `unproductive.ts` and `creation-completion.ts` straddle too. Second, the `delivery.ts` description was wrong in its particulars: it is **not one value computed in assembly and consumed by the stream wrapper** — it is TWO DIFFERENT EXPORTS on two paths (`deliveryModeFor` on the returned handle in `proxy.ts`, `typicalDurationMs` in the stream wrapper at `api.agent.ts`). Writing this spec's version into `spec/agent-seams.md` would have made the document false on day one, which is the failure the document exists to prevent.
24. 🔴 **A source scan makes the naming durable.** Default-deny, in the `budgets-wiring.spec.ts` / `outbound-enumerate.spec.ts` family: it enumerates the modules `proxy.ts` and `api.agent.ts` actually invoke, and fails on any participant not classified in the sub-spec. A document that rots is worse than no document, because it is read as current.
25. **The scan carries its own CONTROLS** — that it found the real module, that comment-stripping did not eat the region, and that every construct the assertions target is locatable. `budgets-wiring.spec.ts:82-99` is the template, and its header states the reason: *"a scanner whose pattern silently stops matching reports a clean bill of health forever."*
26. 🔴 **Explicitly REJECTED, recorded so it is not proposed as the obvious next step:** a plugin registry, an event emitter, reversible effects, config-composed pipelines, or any port of Cordis. §4.2's stance forbids it; the brief does not ask for it; and the seams' current form — a call order in one file — is *readable*, which a dynamically-composed tree is not.
27. ⚠️ **`MAX_MEDIA_ROUNDS` no longer exists** — deleted 2026-08-08 by owner decision (`media-tools.ts:65-76`: *"THERE IS NO MEDIA ROUND BUDGET"*), with live evidence of three refused images. Every remaining mention is a comment or a test post-mortem. It must not appear in the classification, and any text asserting the constant will not compile.

### E. Recording the foundation decision

28. **A §2.1 entry, beside the standing pull-compatibility commitment it answers, indexed from a new §8k decisions log** (⚠️ two intermediate corrections were wrong here: the first claimed §8 "carries no decisions log", the second said it carries eleven. §8 through §8j carries TEN — §8c is a *Provider matrix* — and §8k makes eleven. See spec_impact item 6.), records: `dsh` evaluated 2026-08-21; **bolt.diy stays the base**; the reason is that the two replace *different halves* — bolt.diy supplies the client workspace (sandbox mount, preview, terminal, `FilesStore`, workbench, the `boltArtifact` protocol, the chat surface) and `dsh` supplies an agent loop we already replaced with a server-side one that has the credit gate, the tier and provider ladders, the cache-breakpoint budget and the settlement threaded through it.
29. **The three structural blockers are recorded with it**, because "we looked at it once" is not a decision a future reader can act on: `dsh` has no multi-tenancy (no user, balance, ownership or two walls); its tools execute against a real filesystem and real subprocesses behind an approval policy, which §5 forbids on our infrastructure; and it is a developer preview promising breaking changes on a research framework, which would put a second, less stable upstream underneath the money path against §2.1a's single-upstream commitment.
30. **The steelman is recorded and answered**: using `dsh` server-side as a loop library only fails because several of our tools are **client-executed** — the MCP relay, the preview tools, media delivery — deliberately, so that one generation stays alive for **one settlement** rather than fragmenting billing across re-POSTs. That is a fight over the exact seam the billing model depends on.
31. **§10 gains an open question**, not a task: whether a `dsh-plugin` presence is worth having later as a distribution channel into a developer's local loop. Not now — developer preview, breaking changes.

### F. Out of scope

32. **The enhancer path** (`api.enhancer.ts`) is a second model call with its own settlement and is **not** fingerprinted in v1 — named here so its absence is deliberate rather than an oversight.
33. **The inherited `/api/chat` / `/api/llmcall` paths** are fail-closed and get nothing.
34. **No wire-level byte comparison** — see edge case 1. The invariant compares what the **assembler** owns; the bytes below it are legitimately mutated by the transport.
35. **No new user-facing surface.** The `/context` report and the chip are untouched; this is an operator instrument.

## Possible Edge Cases

1. 🔴 **The transport legitimately mutates the body after assembly, so a naive wire comparison fires on every single turn.** `thinkingFetch` (`capabilities.ts:288`) `JSON.parse`s the final body and writes `thinking` / `output_config`; `refusalFallbackFetch` adds `fallbacks` and a beta header; the SDK adds its own framing. This is the single biggest design trap in the feature: the invariant compares **the fields the assembler owns**, and any post-assembly mutation must be a declared, named allow-list — never an implicit tolerance.
2. **`thinkingFetch` is the only place the literal wire body exists as a value**, and it early-returns untouched for a non-Anthropic provider or an unrecognised model id, and holds no `generationId`. So it cannot be the seam; it can at most corroborate.
3. **A generation that fails before `startStream`** — gate refusal, `NotConfiguredError`, a claim conflict — has no fingerprint. "No fingerprint" must be distinguishable from "the fingerprint was empty", the `remoteHead` `undefined`-vs-`null` distinction one subsystem over.
4. **Media rows share the `generations` table** (`med_*` ids, `media/service.ts:376`). They have no request and must produce no integrity alert; the Admin report must not divide by them.
5. **BYOK turns** run on the user's key but are still our record; they are fingerprinted identically. The fingerprint must never capture a key, and no key is in the assembled arrays to capture.
6. **FS mode vs Supabase must not diverge again.** A new field written by one store and not the other recreates live defect 1 under a new name.
7. **A first build turn's sentinel check must not fire for an imported or remixed project**, whose tree legitimately does not contain the §4.4b scaffolded class.
8. **A legitimately tiny project** (a nearly-empty repository import) must not trip INV-3's shrink check.
9. **A conversation that legitimately drops files** — the user deletes half the project — is a real shrink and must be distinguishable from a lost map. It is not, from the server's side; the alert is therefore a signal, not a verdict, and its copy must say so.
10. **Two tabs on one project** interleave chats through the same process; the in-process last-seen map is keyed by chat, not project.
11. **A long turn with several re-issues** produces several fingerprints; the record's size must stay bounded, and the Admin report must not treat a four-fingerprint turn as four turns.
12. **`historyStats` is measured post-compaction** and is already recorded; the fingerprint must agree with it or one of the two is wrong — which is itself a useful invariant and the cheapest one in the feature.
13. **The hash of a system block containing the project's `CLAUDE.md`** changes whenever the user edits that file, correctly. The invariant must never treat *changed* as *wrong*.
14. **`settleAfterCreation` reaching its ceiling** is documented as *"normal and silent"* — a project whose tree never quiesced proceeds with an unknown-completeness map, and INV-3(a) is the first thing that would notice.
15. **A turn whose model is swapped by the fallback** changes the model mid-stream; the fingerprint records the model *requested*, and the handoff record carries the model that *served*. Both are needed; neither alone is the answer.

## Acceptance Criteria

1. A `RequestFingerprint` is computed inside `startStream` and is produced for **all SIX** call sites (corrected from five — see requirement 2), each passing a distinct `kind` literal. Pinned by `fingerprint-wiring.spec.ts`: exactly one `computeRequestFingerprint` call, six labelled call sites, six distinct labels, and the scalars shared with `_streamText` rather than re-specified. ⚠️ `runAgentGeneration` cannot be constructed in a unit test (it boots the prompt store, the ledger and a provider), so "a continuation produces two fingerprints with distinct kinds" is established STRUCTURALLY — `requests.push` is unconditional inside the closure and the labels are distinct — plus a value-level test that the two shapes differ. Mutation-verified both directions.
2. The fingerprint contains **no file body, no message text and no system-block text** — asserted by a test that plants a recognisable secret string in a file, a message and a system block, and greps the serialized fingerprint for it. Mutation-verify by adding the raw text and confirming the test fails.
3. The fingerprint is **byte-identical for two structurally identical requests** presented with different object key orders — the determinism control, without which every later assertion is noise.
4. **INV-1** flags a map carrying both spellings of one file, naming both, **with a control** proving two genuinely different files do not flag. The same predicate is applied to `createFilesContext` and `buildFileManifest`, and a test proves the two implementations agree on a shared table of cases.
5. **INV-2** flags a `<boltAction type="file">` body that survives into the post-`convertToCoreMessages` array — the check `history.spec.ts` structurally cannot make. **Control**: a `shell` action's one-line command, and a body shorter than the `OMITTED` marker, both pass.
6. **INV-3(a)** flags a first build turn whose manifest lacks the framework sentinel, and — when a caller can NAME it — the scaffolded class, **with a control** proving an imported project (which has no scaffolded class to name) does not flag. ⚠️ **As shipped only the sentinel half is live**, because the class's name never reaches the server: see Known gaps #1. **INV-3(b)** flags a manifest that shrank past the threshold within one chat, with a control for a legitimate small project.
7. **INV-4** flags a turn whose serving model differs from the recorded model.
8. 🔴 **A violation does not fail the generation.** A test drives a turn with a deliberately violating request and asserts the stream completes, the credits settle normally, and the alert fired. Mutation-verify by making the guard throw in production mode and confirming this test fails.
9. **A violation DOES throw under test** — the same fixture, asserted in both directions, since a guard that only ever reports is a guard nobody will notice going quiet.
10. **The alert is rate-limited**: N violations in one window produce one alert, with a control proving a violation after the window still alerts.
11. 🔴 **Migration**: `raw_stops`, `fallback_handoffs`, `blocks_loaded`, `request_fingerprints`, `integrity_issues` exist; a Supabase round-trip preserves all of them. **The test that matters** is the structural one: every `GenerationRecord` field is written by the store, filled by a database default, or explicitly declared derived-on-read (three kinds, not two). Mutation-verify by adding an unwritten field and confirming the test fails.
12. **A fallback handoff survives a Supabase round-trip** — the direct regression test for live defect 1.
13. `spec/agent-seams.md` exists, classifies every participant, and names **every** straddler with its reason. ⚠️ This said "the two straddlers" until 2026-08-21; there are TWELVE (see the correction on requirement 23), and an Acceptance criterion asserting two could only be satisfied by a document that was false.
14. **The seam scan fails when a new participant is added to `proxy.ts` or `api.agent.ts` without being classified**, and passes when it is — mutation-verified in both directions, with its own CONTROLS proving the scanner reads the real modules.
15. The scan contains **no mention of `MAX_MEDIA_ROUNDS`** and the suite compiles.
16. **SPEC.md is updated in the same PR** — §4.2 step 2a pointing at the byte-identical architecture stance (⚠️ not "restated" — see spec_impact item 1), §4.2.8's verifier row, §4.10/§5A's alert signal, §4.2a's `fallbackHandoffs` correction, §4.5.5's columns, the §2.1 foundation decision with its §8k index entry (⚠️ an intermediate correction wrongly claimed §8 has no decisions log) and the §10 open question; plus the `spec/context-budget.md` rows.

## Known gaps at ship time (recorded so none of them is silent)

Found by the adversarial verifiers during execution, decided rather than left to be rediscovered:

1. **INV-3(a) checks the FRAMEWORK sentinel only.** The proxy does not pass `scaffoldedClassPath` because the class's name is a client-side fact (`create-project.ts` derives it from the project title) and the server is never told it. A heuristic stand-in — *"the manifest contains no `src/scripts/` file"* — was built, tested, and **rejected**: it fires on every legitimately imported or remixed project (edge case 7), which is the noisy-in-week-one failure that mutes a channel. The parameter stays, exercised by tests, ready for the turn that can name the class. The framework file is the one that was actually missing in the incident this was written for.
2. **INV-4 cannot see a store that drops the column.** It reads the field off the payload about to be persisted, so it catches an edit that stops writing it; the store-level failure is one layer down and is guarded structurally by `FIELD_COVERAGE` + `field-coverage.spec.ts`. ⚠️ Its first implementation was `checkHandoffRecorded(x, x)` — the second argument derived from the first one line above — and therefore incapable of firing for any input. Caught by a verifier, not by a test.
3. **`buildFileManifest` does not apply `IGNORE_PATTERNS`; `createFilesContext` does.** The two paths now share one de-dup rule and still disagree about MEMBERSHIP. Pre-existing, orthogonal to this feature, and near-zero impact while `createFilesContext` is dead on the product path — but it means an ignored file duplicated under both spellings is one collapse on the manifest and none on the context. Worth a deliberate decision, not an accident.
4. **`generationKind` answers `'other'` for an unrecognised prefix, and `buildUsageReport` filters `!== 'media'`** — so an `'other'` row still joins the generation numbers. Tightening to `=== 'generation'` is NOT safe today: legacy rows predate the `gen_` prefix, so it would silently drop historical turns out of the report an operator reads history with. Recorded in the code as a decision.
5. **Media spend is reported BESIDE the generation counters, never inside them.** Excluding `med_*` rows was the fix; excluding them without a counterpart made real KIE money vanish from a panel headed "Usage & cost" — *a fix blinding the metric that measured it*, this codebase's most-recorded failure shape. `UsageReport.media` and a panel row are the counterpart, and `sampled` (rows read) is now explicitly a different number from `report.generations` (turns aggregated).
6. **`OMITTED_MARKER_CHARS` has 12 characters of headroom, and that is not slack in a safe direction.** A marker growing past the floor makes INV-2 fire on every compacted request. A drift test reads `history.ts` and fails the moment the literal changes at all, in either direction.

## Open Questions

1. ~~**Should INV-3(b)'s shrink check ship enabled, or dark for one release?**~~ **DECIDED (owner, 2026-08-21): recording-only.** This feature is sequenced ahead of `github-branch-client`, whose branch switch, discard and pull make a large legitimate file-map change a ROUTINE operation rather than the rare one edge case 9 assumed. Recording-only defers the noise question to the feature that creates it, and avoids shipping a suppression hook with no caller. Promotion to an alert is a task in the branch feature's plan, not here — see requirement 12 and `_specs/github-branch-client_plan.md` T15.
2. **Does the fingerprint belong on the `generations` record at all, or in its own table?** It is bounded and read-whole, which is migration 0002's stated case for `steps jsonb`; but a turn with several re-issues makes the row wider than anything else in the table. Recommendation: `jsonb` on the row, and revisit only if a real row gets large.
3. **Should `historyStats` and the fingerprint's message hash be reconciled automatically?** They measure the same array by two routes, which makes them a free cross-check — but it is also two numbers that will disagree for uninteresting reasons the first time an SDK version changes `convertToCoreMessages`.
4. **How long are fingerprints retained?** The record has no retention policy today. If one is ever added, the fingerprint is the first thing that should age out, being the largest and the least useful after the fact.
5. **Should the enhancer be fingerprinted?** It is a real model call with a real settlement, and it has already produced one billing defect (`promptTokens` reported 0 for its whole life). Out of scope here; worth its own decision.
6. **Does INV-4 belong in this feature or in §4.2a?** The fallback-handoff gap is arguably an Anthropic-provider defect that this feature merely *found*. Landing the migration here is right; whether the invariant lives beside the fallback code is a placement question.
7. **Is the in-process last-seen map acceptable, given more than one server instance?** It is per-process, so a user's turns can land on different instances and the shrink check simply will not fire. Acceptable for a signal; unacceptable if it is ever promoted to anything stronger.

## Testing Guidelines

⚠️ **This repository does NOT use a `./tests` folder.** Tests are colocated `*.spec.ts` / `*.spec.tsx` files beside the code they exercise, run by Vitest (config lives in `vite.config.ts:105-114`; there is no `vitest.config.ts` and no setup file). React specs open with `// @vitest-environment jsdom` on line 1. Follow that convention.
⚠️ **A spec file must never live in `app/routes/`** — Remix compiles it as a route, the manifest imports `vitest` at runtime, and every request 500s.

Add or extend, keeping each suite meaningful rather than exhaustive:

- **`app/lib/.server/agent/request-fingerprint.spec.ts`** *(new, pure — the highest-value suite here)* — the fingerprint's shape, determinism under key reordering, the no-bodies assertion with a planted secret string, and attachment-by-reference. **Mutation-verify** the no-bodies test by including raw text.
- **`app/lib/.server/agent/request-invariants.spec.ts`** *(new, pure)* — INV-1 through INV-4, each with the control named in Acceptance. The controls are the point: a de-dup assertion alone passes for a function that collapses *everything* to one entry, which is the same bug pointing the other way — the lesson `files-context.spec.ts:43` already records.
- **`app/lib/.server/agent/fingerprint-wiring.spec.ts`** *(new, source scan)* — that the fingerprint is computed inside `startStream` and not at one call site, and that all SIX call sites route through it, each with a distinct `kind` literal. Built on `budgets-wiring.spec.ts`'s pattern **with its CONTROLS describe**, since "exactly one call" is precisely the shape that scan already proves for `resolveAgentBudgets`.
- **`app/lib/.server/agent/seam-classification.spec.ts`** *(new, default-deny source scan)* — every participant `proxy.ts`/`api.agent.ts` invokes is classified in `spec/agent-seams.md`. Mutation-verified both directions, with scanner controls. ⚠️ Do not silence a failure by adding an allow-list entry.
- **`app/lib/.server/billing/generations.spec.ts`** *(extend)* — the structural test that every `GenerationRecord` field is written by the store, filled by a database default, or declared derived (three kinds — ⚠️ this said "both stores or derived", the two-kind framing corrected at requirement 19); ⚠️ it shipped as the new `field-coverage.spec.ts` + `generation-record-roundtrip.spec.ts` rather than by extending `generations.spec.ts`; a Supabase round-trip preserving `fallbackHandoffs`, `rawStops`, `blocksLoaded` and the new fields.
- **`app/lib/.server/billing/ledger-sql.spec.ts`** *(extend)* — the new columns asserted against the **real migrations** in the PGlite harness, following the existing rule that the TS mirror proves we wrote the rules twice, not that the database enforces them.
- **`app/lib/.server/agent/proxy.spec.ts`** *(extend, or a new colocated suite)* — a turn that forces a continuation produces two fingerprints; a violating turn completes and settles normally in production mode and throws in test mode.
- **`app/lib/.server/admin/usage-report.spec.ts`** *(extend)* — the new counters, with a control proving `med_*` rows are excluded.

**Default-deny guards that must still pass:** `no-server-storage.spec.ts` and `one-working-copy.spec.ts` (nothing here may become server-side project storage), `cache-breakpoints.spec.ts`, `budgets-wiring.spec.ts`, `money-paths.spec.ts`, `transport-envelope.spec.ts`, `first-build-turn.spec.ts`, `outbound-enumerate.spec.ts`.

**Mutation-verify every guard this spec names as mutation-verified.** The recorded lesson in this codebase is that a test whose input cannot reach the rule it names is not a weak test, it is no test — and this feature is an entire suite of guards whose only job is to fail.
